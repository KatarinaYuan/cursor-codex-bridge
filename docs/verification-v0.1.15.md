# v0.1.15 验证范围

本版处理 Cursor 导出用户消息时压缩连续空行，使已提交的原生消息无法绑定正式来源、旧预览长期显示运行中的情况。输入原文、正式导出正文和来源归属分别验证；显示收尾不能倒推提交归属或触发重发。

## 新提交的导出凭据

导出投影仅将 CRLF 归一为 LF、沿用首尾空白修剪，并将至少三个连续 LF 压为两个 LF。实际粘贴、提交内容、原生用户消息及其原文哈希保持完整。普通换行、内部空格及其他正文差异不能借此忽略；全文草稿核验和唯一提交规则继续适用。

只有新鲜确认的原生提交可使用 `v3` 凭据，分别保存原始输入摘要和导出正文摘要，并保留原客户端消息 ID、模型、原进程及精确来源消息映射。来源仍须唯一且稳定；相同投影存在竞争来源时，不能选择其中之一。既有 `v2` 凭据继续使用原有严格正文语义，不自动迁移成宽松匹配。

## 旧未绑定预览的显示收尾

旧预览没有提交来源凭据时，不能仅凭正文相同追认归属。自动收尾须同时核对：

- 只有一个符合结构的原生候选，客户端消息 ID 唯一，没有既有来源映射、其他运行轮次、排队请求或未提交草稿。
- 原文包含被压缩的连续空行，投影确实改变正文；除此之外没有差异，投影后的正文与正式来源完全一致。
- 只有一个匹配的稳定来源，明确成功完成；其时间戳位于原提交所在分钟起的两分钟窗口内。
- 来源前缀均明确完成，最新请求的稳定封套唯一，位于匹配来源之后，时间戳严格更晚。
- 仍为原会话、工作目录、pane、进程及进程启动时间；重新核对绑定并捕获画面，精确对应最新请求的受支持忙碌状态或完整 `Clarifying Questions` 提问框。空闲画面还需完整来源已结束。

旧预览保留原生轮次、消息、客户端消息 ID 和原文，记为已中断并解释导出差异造成归属未确认。完整正式回复独立导入，不声明旧预览成功，也不为其生成来源归属凭据。没有明确结束证据的最新请求不进入完成历史，继续使用自身来源观察。

持久化收尾记录保留原文摘要、客户端消息及诊断依据，阻止以后历史扫描重新合并旧预览。相同客户端消息 ID 和相同输入重试只返回旧轮次；输入不同或凭据无法核对时拒绝，不重新粘贴或提交。桥重启、重复扫描和来源暂时变化后也需保持这一行为。

重复封套的既有恢复范围见 [v0.1.14 验证说明](verification-v0.1.14.md)。本版的显示收尾和后续观察不向原 Cursor 输入、不修改原历史、不清空草稿、不改变模型，也不重启 Agent。提问框识别只允许观察，回答仍在原 CLI 完成。

## 验证记录与部署验收

发布前本地回归已覆盖上述边界：全量 Node.js 测试 644 项通过、0 项失败，另有 16 项 Linux 专用测试在 macOS 跳过；Python 安装器测试 31 项通过。生产桥集成测试 5 项通过，覆盖先扫描后附着的启动顺序、旧无凭据预览收尾、精确重试防重发、后续独立请求完成和 v3 重启归档。安装相关的 75 项定向测试包含官方 `v0.1.14` fixture、备份、自定义保护与幂等。

这些测试不替代实际部署验收。具体部署需另行核对冻结发布包与运行文件的逐文件摘要、原 Cursor 进程与模型、完整正式回复和原生聊天完成状态；实际部署结果记录在对应 GitHub Release 中，不把暂存或只读 API 连通记为升级完成。

验收期间不向正在运行的业务会话发送校验消息。原生聊天应保留原始用户换行，结束旧预览的运行状态，独立显示已明确完成的正式回复，并按最新请求的真实状态继续同步。若用户任务仍在运行或等待选择，应保留相应状态，不代答、不清草稿、不重启 Agent。
