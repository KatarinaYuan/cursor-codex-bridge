# 故障排查

先在 laptop 的仓库目录运行：

```sh
node cli.mjs doctor --ssh my-dev
```

使用安装时的源 SSH 别名。诊断只检查配置和程序状态，不发模型请求。`--json` 方便保存结构化结果；公开前仍需检查和脱敏。

如果安装时指定了 `--alias my-cursor`，这里及后续升级、卸载也必须带同一选项，例如 `node cli.mjs doctor --ssh my-dev --alias my-cursor`。

## SSH 正常，但 App 没有显示 Cursor 模型

- 在 App 的 SSH 连接设置中添加或启用安装器输出的桥别名，并选择该连接下的项目。
- 检查 `doctor` 是否确认桥专用环境生效。安装器依次检测 `CODEX_HOME` 和 `LC_CURSOR_CODEX_BRIDGE` 转发；两者都被拒绝时，需要管理员允许相应变量。安装器不修改 `sshd_config`。
- 不要把普通 Codex 连接误认为桥连接。桥和普通连接有不同别名、状态目录和 wrapper。
- 若 App 尚未刷新，断开该桥连接后重新连接。不要重启原 tmux Agent 来刷新 App。

## 找不到 Node、Cursor 或 Codex

交互式 shell 中可用的命令未必在 SSH 登录环境中可用。可用 `--node-path`、`--agent-path`、`--codex-path` 指定**远端绝对路径**；不要传 laptop 路径。

缺少 Node.js 22+ 或原版 Codex CLI 时，安装器自动下载固定版本并校验摘要，保存到用户私有运行时目录。下载失败时检查开发机到 `nodejs.org` 和 `registry.npmjs.org` 的 HTTPS 网络；不要跳过校验。远端需 Linux glibc x64/arm64、Python 3.8+ 和 bash，musl 不受支持。

Cursor 登录属于远端用户环境。使用正确 SSH 用户并由账号拥有者完成登录；不要把登录 token 或他人的凭据放入仓库。

## 旧会话没有出现或历史没有刷新

空会话要先在 Cursor CLI 中产生可读取的消息。默认扫描当前 SSH 用户的 `.cursor`；不同用户、不同来源目录的历史不会自动混合。没有 tmux 实时绑定时，更新时间取决于 Cursor 写入 transcript 的时机。

如果历史路径可读而仍未发现，报告 Cursor Agent 版本、安装版本和脱敏的诊断结果，不要上传真实 transcript 或数据库。

## Cursor 会话被误列为置顶，没有出现在 Recents

`v0.1.4` 修复了桥接服务忽略分区筛选、把普通 Cursor 会话也返回到置顶查询中的问题。升级到该版本后，会话按实际活动时间参与原生最近列表；不会通过重写更新时间把旧会话强行排到前面，也不会改变 Cursor 会话或模型。

在 laptop 任意目录运行，把 `my-dev` 换成安装时的源 SSH 别名：

```sh
npx --yes --package=https://github.com/KatarinaYuan/cursor-codex-bridge/releases/download/v0.1.17/cursor-codex-bridge-0.1.17.tgz cursor-codex upgrade --ssh my-dev
npx --yes --package=https://github.com/KatarinaYuan/cursor-codex-bridge/releases/download/v0.1.17/cursor-codex-bridge-0.1.17.tgz cursor-codex doctor --ssh my-dev
```

原来使用自定义桥别名时，两条命令都补上相同的 `--alias my-cursor`。若升级和诊断通过而 App 仍显示旧列表，在 SSH 设置中断开桥连接后重新连接。全局最近列表有条数上限，较旧会话未进入当前列表不代表丢失；仍可在对应项目中查找。诊断和列表检查不会发送模型消息。

## 不能向现有 tmux 会话发送

确认 Agent 处于同一用户的默认 tmux server，使用受支持的终端布局，并且输入框为空、当前轮次结束且没有菜单或审批。模型切换、审批和自由文本回答先在原 CLI 处理。

若出现 `unrecognized-footer-or-overlay`，表示输入框下方的状态栏或附加界面未通过识别。窄终端中的路径和分支换行曾触发误判；`v0.1.2` 支持在右边缘空格后换行的分支分隔符。`v0.1.17` 还支持完整的 ` · ` 恰好结束于右边缘、分支名单独换到下一行的布局。这种误判可能只影响发送，历史和回复仍可同步。升级后重新连接桥即可加载修复。此错误也可能来自真实菜单或审批，不能据此认定输入框为空；不要自动清空草稿或按键关闭未知界面。

若出现：

```text
Cursor input changed or could not be verified after paste;
text remains as an unsubmitted draft in tmux. Review it in Cursor CLI
```

这表示桥未能确认粘贴后的输入，文本可能仍作为草稿留在 CLI 中。**不要盲目重复发送或再粘贴一遍。**先在 Cursor CLI 查看草稿及是否已产生回复。只有持久化恢复凭据、原进程、模型、历史和草稿原文全部一致时，桥才允许将相同原文作为已有草稿重试；它不会自动清空或提交普通草稿。

`v0.1.10` 修复另一种多行草稿误拒绝：核验光标经过绝对附件路径中的斜杠时，Cursor 可能显示灰色 `No matches` 补全菜单，暂时遮住模型状态栏。桥仅在独占输入的只读扫描中、光标位于预测的斜杠片段、草稿视口完全未变且菜单精确匹配时继续；不编辑正文，不按 Escape。扫描结束后必须回到草稿末尾，并重新确认完整的原模型状态栏，才会移除校验标记并发送唯一一次 Enter。未知菜单、视口变化或末尾仍显示斜杠菜单时继续拒绝提交，保留原文、换行与恢复凭据。诊断只记录有限的核验元数据，公开前仍需脱敏。升级不会自动提交已有失败草稿。

`v0.1.8` 修复了中英文混排短消息的一种误拒绝：桥按终端显示宽度预测能放入六行，而 Cursor 的输入布局可能额外换行，隐藏最上面一行，导致原文无法完整核验。这不等于 SSH 已断开。新版在粘贴前更保守地规划临时列宽，同时按输入布局核验草稿；保留尾部换行及空行，无需手动拉宽窗口。升级不会自动提交已经留下的草稿；只在相同原文及完整恢复凭据均通过核对后才允许显式重试。若仍不匹配，继续保留草稿并拒绝发送 Enter，不会跳过核验。

`v0.1.6` 修复了短消息超过六个显式文本行时的发送限制。消息不超过 800 个 UTF-16 字符且含超过六行时，桥会临时独占原 pane 的输入，阻止普通 tmux 按键混入，原文只粘贴一次，再移动光标检查全文。临时随机标记帮助识别连续空行；核验完成后先删除标记，再发送一次 Enter。提交原文保留空行、内部换行及首尾换行，不补字符、不合并段落，也不打开外部编辑器。看到旧的 `more than six hard lines; no text was pasted` 错误时，先升级到当前 `v0.1.17` 并运行诊断。

核验期间请等待临时输入锁自动释放。输入锁最多保留 300 秒，并有独立看门狗负责清理。已有 `pipe-pane`、已经关闭的 pane 输入、草稿或无法确认的布局会使桥拒绝接管。核验失败时不发送 Enter，保留草稿；如果提交是否成功的确认不明确，桥不会自动重发。

若错误明确提示 `temporary verification marker`，同一消息的显式重试只有在完整草稿、标记、进程、模型和来源历史均验证一致时才会删除标记并提交；不会再次粘贴正文。若标记输入或删除的确认不明确，则拒绝自动恢复。不要手工提交带有校验标记的草稿。

窄窗口的软换行仍通过临时增加列宽处理，仅支持独占、未缩放且所需列宽不超过 1007 的 tmux 窗口。提交或失败后恢复原尺寸，并保留 `window-size` 原有的显式配置或继承关系；若有人同时调整布局或选项，桥会保留对方改动。超过 800 个 UTF-16 字符的粘贴继续使用 Cursor 自己的折叠标记，并核验同一会话保存的完整内容。这些检查只适用于共享现有 tmux 的代发路径。

错误在历史中保留不代表发生了新的发送请求；排查时区分旧失败记录、重新打开聊天和新的发送尝试。输入框布局、进程状态或模型格式不兼容时，代发会被拒绝。请提供 Agent/App 版本和脱敏诊断，保留草稿待检查。

## Cursor 已结束，但 App 一直显示 thinking

先区分真实任务与桥中的观察轮次。旧版桥可能在正式历史已完成后，根据终端残留的忙碌画面创建第二个运行轮次；回复正文可以同步到这个轮次，但它等不到属于自己的新来源完成事件，因而一直显示运行中。仅凭 `thinking` 或终端最后一段文字不能判定 Cursor 是否仍在执行。

`v0.1.5` 按来源轮次 ID 检查正式历史，避免从已完成的来源创建重复观察。新建的观察同时持久化来源轮次与原生轮次的对应凭据；重连后继续观察原任务，或从正式完成记录收尾，不重发模型请求。升级命令见上文，普通安装器仍要求桥空闲。

`v0.1.7` 进一步区分真人请求和 Cursor 注入的完整运行时工具目录。真人请求的完整时间戳封套提供稳定身份，避免 transcript 截取后的位置编号碰撞；运行时目录不再拆开同一次请求。相同正文的不同请求不应互相替代。旧格式缺少完整封套时仍兼容当前会话匹配，但不建立新的稳定提交恢复凭据；重复封套拒绝自动归属，不靠提示词相同猜测完成事件。

`v0.1.13` 对其中一种旧外部观察自动收尾：记录须能证明它是 `v1` 外部观察，原本稳定的完整封套后来出现重复，完整来源已完成，仍绑定原先同一存活进程，并且新捕获画面显示输入可用、任务不忙碌。桥保留旧预览为已中断，解释来源归属丢失，再完整导入正式完成的来源卡片；不会把重复来源当作新的实时归属，也不向 Cursor 输入、清空私人草稿或改变模型。检查会周期重试，桥重启或历史内容未改变也不会阻止后续核对。

`v0.1.14` 增加严格的后续请求边界，适用于有效 `v1`／`v2` 观察：歧义组及前缀已明确完成，最新来源封套唯一、位于整个歧义组之后且时间戳严格更晚，再核对同一原进程和精确匹配最新请求的忙碌画面或受支持提问框。旧预览保留为已中断，正式完成回复独立导入；最新未完成请求继续观察。来源歧义本身不能授权重发、重绑或假报完成。缺少这些证明、原进程无法核对或画面不支持时，不自动处理。请保留记录并提交脱敏诊断；不要结束 Cursor 进程、删除状态目录、手改轮次状态或给原聊天重复发消息来清除显示。普通安装器仍拒绝忙碌升级；应报告具体阻断原因，不能把显示异常当作强制升级的许可。

`v0.1.15` 还处理一种已经提交、却未能绑定来源的多行消息：Cursor 的 JSONL 导出会把连续至少三个 LF 压成两个 LF，而原生请求保留完整原文。新版只在导出比较中使用这一窄投影，以 `v3` 凭据分别保存实际原文与导出正文摘要；不会合并普通换行、删除内部空格或放宽粘贴核验。

旧未绑定预览只有在唯一已完成来源、提交时间窗口、已完成前缀、严格更晚的稳定最新请求和原进程新鲜画面等证据均成立时，才会被记为已中断，正式回复单独完整导入，最新请求继续跟踪。它不会被追认为成功提交的来源所有者；持久化收尾凭据阻止以后误合并或相同客户端消息重试时重发。存在其他归属、歧义、排队请求、未提交草稿或不匹配画面时继续拒绝处理。不要手动删空行、改状态或重复发送业务消息来清除 thinking；该版本验收范围见 [v0.1.15 验证说明](verification-v0.1.15.md)。

`v0.1.16` 处理另一种阻塞：旧原生显示没有建立来源凭据，正文又与正式来源不同，不能归属；整条聊天的运行屏障同时挡住后来已完成的回复和真实新任务。显示收尾不需要把两段正文视为相同，但必须具备独立证据：同一原进程和会话、既有映射的已完成前序来源锚点、原生开始所在分钟起的近邻完整稳定来源、已完成的中间前缀，以及严格更晚的稳定最新请求和相符的新鲜画面。

满足条件后，只把旧显示原文和客户端消息保留为已中断，记录显示收尾凭据，再独立导入正式完成来源、继续观察最新请求。旧显示没有因此获得来源归属，不会被改报为成功。最新 transcript 尾部即使解析器暂写 `completed`，没有明确结束记录也不会进入完成历史。普通 CLI 草稿保持原样；当前任务仍忙碌或在提问时按真实状态继续显示，不代答、不清草稿、不改模型、不重发业务消息。缺少来源锚点、进程或最新画面等证据时继续拒绝收尾；范围与验收状态见 [v0.1.16 验证说明](verification-v0.1.16.md)。

## 升级或卸载提示忙碌

等待现有桥任务完成后再运行命令。若状态与 App 显示不同，先查看诊断，不要直接 `pkill node`、`pkill agent` 或删除 socket。这些命令可能影响其他任务。

安装器不会管理之前手工部署的旧桥，也不会迁移其记录。若旧服务不支持 maintenance RPC，应按旧部署自己的说明处理；不要把它误认为新安装的服务。

## 提交问题

说明操作步骤、发生时间、期望和实际结果，以及安装器/Node/Agent/Codex/App 的版本。附上经过检查的 `doctor --json` 输出。不要上传 SSH 私钥、登录 token、聊天记录、tmux 完整画面、Cursor 数据库或含个人配置的压缩包。更多说明见 [隐私与问题反馈](security.md)。
