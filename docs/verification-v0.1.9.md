# v0.1.9 验证范围

本版修复已提交请求与正式来源历史之间的绑定保存，以及旧失败预览的显示顺序。它保留 v0.1.8 的输入布局核验和原文换行保护。

已识别到某一固定来源轮次后，若验证状态曾中断，恢复后可在当前验证周期内重新尝试保存该轮次的绑定。重试要求原会话、进程、模型及来源仍一致，同一时间只有一次尝试，失败后退避。此处重试的是绑定保存，不重新粘贴草稿、发送 Enter 或调用模型；未知提交结果仍不得自动重发。

显示顺序修复只适用于严格证据能确认的孤立旧失败预览：后续正式来源历史已导入，原失败记录缺少可用来源绑定，且来源映射及恢复凭据能排除其他请求。只调整其在同一聊天中的位置，保留原错误、原生聊天／轮次／消息 ID、模型、客户端信息、来源映射和恢复凭据。来源缺失、重复或有歧义时不自动修正，也不改写原 Cursor transcript。

验证应分别覆盖恢复后的绑定重试、并发排除、退避、验证周期变化、原进程或来源变化时拒绝绑定，以及顺序修复的正例与拒绝条件。安装器另外验证未修改的官方 v0.1.8 skill：两个官方文件均匹配时先保留完整备份，再原子更新；定制正文、元数据、额外文件或符号链接仍拒绝覆盖。

自动化验证已运行：Linux 完整套件 509/509 通过；随后新增的官方旧版 skill 分发变更通过安装管理测试 47/47；真实 JSON-RPC 隔离集成测试 29/29 通过，包括暂时失去前台验证后恢复且仅发送一次 Enter，以及断开后恢复原聊天历史顺序。安装 skill 通过系统 skill 校验，`git diff --check` 通过。隔离集成使用合成历史，不向模型发送请求。真实环境的运行包、原生聊天缓存和保留 Cursor 模型的消息往返验收，单独记录在 [本版 Release 说明](https://github.com/KatarinaYuan/cursor-codex-bridge/releases/tag/v0.1.9)；不要把自动化测试当作真实部署结果。

Codex App 对已加载的同 ID 轮次可能保留旧数组顺序。服务端 `thread/read`、`thread/resume` 或 `thread/turns/list` 返回正确顺序，不等于当前 App 缓存已重新排序；SSH 重连也不保证清除该缓存。客户端缓存重新加载是独立验收步骤，不能伪造归档、回滚、压缩等事件来宣称显示已刷新。

输入布局与失败草稿的保护范围见 [v0.1.8 验证说明](verification-v0.1.8.md)。安装、诊断和自动化测试通过均不能替代真实 App、SSH、Cursor 与原 tmux 会话组合的验收。
